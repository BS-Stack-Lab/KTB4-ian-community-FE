# 프롬프트에서만 바꾼 규칙은 다음 실행에 사라집니다: 계약과 문서의 동기화

이번 작업에서는 회원가입 화면을 “Modal 우선” 정책과 다르게 구현해야 했습니다. 프롬프트에 “이번 요구사항에 한해 기존 정책보다 우선한다”고 충돌 순위를 명시했기 때문에 현재 실행은 독립 페이지라는 새 계약을 따를 수 있었습니다.

처음에는 이 결정을 회고 문서의 예시로만 남겼고, 에이전트가 다음 실행에서 실제로 읽는 프로젝트 지침은 수정하지 않았습니다. 이 상태에서는 설명과 실행 규칙이 분리되어 다음 작업이 다시 과거의 결정을 따를 수 있었습니다. 그래서 후속 수정에서 프런트엔드 저장소 루트에 `AGENTS.md`를 추가하고, 회원가입 정책과 계약 변경 동기화 규칙을 실제 프로젝트 지침으로 옮겼습니다.

## 우선순위 명시는 현재 실행만 해결합니다

에이전트가 읽는 규칙을 세 층으로 나눠 보면 문제가 선명해집니다.

```text
사용자의 현재 요구사항  >  가까운 프로젝트 지침  >  전역 기본 지침
```

현재 프롬프트에서 우선순위를 분명히 하면 당장의 충돌은 해소됩니다. 그러나 프롬프트는 작업이 끝난 뒤 저장소의 기준 문서로 남지 않습니다. 다음 실행도 같은 결정을 재현하려면 변경된 계약을 프로젝트 지침에 반영해야 합니다.

즉, 우선순위와 지속성은 별개의 문제입니다.

```text
우선순위: 이번 실행에서 어떤 규칙을 따를 것인가?
지속성  : 다음 실행에서도 같은 결정을 어떻게 재현할 것인가?
```

## 계약을 덮어썼다면 문서 수정까지 완료 조건으로 삼습니다

재발을 막기 위해 다음 규칙을 루트 `AGENTS.md`에 추가했습니다.

```md
## 계약 변경 동기화

- 현재 요구사항이 저장소 문서의 기존 UI·API 계약을 명시적으로 덮어쓰면,
  구현과 같은 변경 범위에서 해당 문서도 함께 수정합니다.
- 영구 변경이면 기존 계약을 새 계약으로 교체하고, 관련 AGENTS.md, README,
  API 문서, 테스트 이름과 fixture를 함께 확인합니다.
- 일회성 예외라면 적용 대상, 적용 기간 또는 종료 조건을 문서에 남깁니다.
- 문서 수정 권한이나 원본 문서의 위치가 불분명하면 완료로 간주하지 않고,
  남은 불일치와 실제 수정이 필요한 문서를 결과에 명시합니다.
```

핵심은 “문서도 가능하면 고친다”가 아니라 문서 동기화를 완료 조건으로 둔 것입니다. 코드만 새 계약을 따르고 지침이 예전 계약을 유지하면 다음 자동화가 코드를 다시 과거 정책으로 되돌릴 수 있기 때문입니다.

## 영구 변경과 일회성 예외를 구분합니다

모든 프롬프트 예외를 영구 규칙으로 승격하면 문서가 오히려 복잡해집니다. 이번 회원가입 화면은 앞으로도 유지할 프로젝트 정책이므로 다음 내용을 `AGENTS.md`에 영구 계약으로 기록했습니다.

```md
### 회원가입 화면 정책

- 기본: 독립 페이지로 구현합니다.
- 레거시 Modal 정책은 기존 화면 유지보수에만 적용합니다.
- 신규 회원가입 흐름에는 적용하지 않습니다.
```

회원가입은 독립 페이지를 기본값으로 고정했고, 레거시 Modal 정책의 범위를 기존 Modal 유지보수로 제한했습니다. 반대로 특정 실험이나 한 번의 마이그레이션처럼 수명이 짧은 예외라면 대상 화면, 기간 또는 종료 조건을 적어야 합니다. “이번만 예외”라는 표현만 남기면 다음 실행이 예외의 유효성을 판단할 수 없습니다.

## 구현 체크리스트에 문서 diff를 포함합니다

코드 리뷰에서도 계약 변경을 놓치지 않도록 완료 전 확인 규칙을 `AGENTS.md`에 함께 추가했습니다. 실제 검토에서는 다음 항목을 확인합니다.

```md
- [ ] 현재 요구사항이 기존 문서와 충돌하는지 확인했습니다.
- [ ] 충돌 시 우선순위를 명시했습니다.
- [ ] 영구 변경이면 AGENTS.md·README·API 문서를 함께 수정했습니다.
- [ ] 일회성 예외면 적용 범위와 종료 조건을 기록했습니다.
- [ ] 테스트 이름과 fixture도 새 계약의 용어를 사용합니다.
```

문서 수정은 단지 설명을 고치는 일이 아닙니다. 테스트 fixture, 모달 이름, 라우팅 용어가 이전 계약을 사용하고 있다면 함께 바꿔야 실제 구현과 검증이 같은 방향을 봅니다.

## 이번 저장소에 반영한 변경

프런트엔드 저장소 루트의 `AGENTS.md`에 두 가지 계약을 실제로 반영했습니다.

1. 회원가입은 독립 페이지로 구현하며, 레거시 Modal 우선 정책을 신규 회원가입 흐름에 적용하지 않습니다.
2. 현재 요구사항이 기존 UI·API 계약을 덮어쓰면 구현과 같은 변경 범위에서 소유 문서를 수정하고, 문서 위치나 권한이 불분명하면 불일치를 남긴 채 완료 처리하지 않습니다.

이 정책은 프런트엔드 UI 계약이므로 백엔드 저장소에는 별도의 `AGENTS.md`를 만들지 않았습니다. 대신 실제 소유 범위인 `community-FE` 루트에 지침을 두어 이후 작업이 저장소 진입 시 바로 읽을 수 있게 했습니다.

## 회고

프롬프트는 현재 실행을 움직이고 프로젝트 지침은 다음 실행을 움직입니다. 충돌 우선순위를 명시하는 데서 끝내지 않고, 이번에는 새 계약을 실제 `AGENTS.md`에 반영했습니다. 앞으로도 요구사항이 기존 규칙을 덮어쓰는 순간을 문서 변경 신호로 보고 코드·테스트·지침이 한 변경 범위에서 같은 계약을 말하도록 관리해야 합니다.
