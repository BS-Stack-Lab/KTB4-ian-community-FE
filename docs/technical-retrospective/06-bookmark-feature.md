# 북마크 기능을 데이터 모델부터 낙관적 UI까지 연결하기

북마크는 아이콘 하나를 토글하는 기능처럼 보이지만 실제로는 사용자별 관계 저장, 중복 방지, 목록 조회, 여러 화면의 상태 동기화, 실패 롤백이 함께 필요했습니다. 이번 구현에서는 북마크를 게시물의 boolean 컬럼으로 두지 않고 사용자와 게시물 사이의 독립된 관계로 모델링했습니다.

## 사용자와 게시물의 다대다 관계를 엔티티로 풀었습니다

한 사용자는 여러 게시물을 저장할 수 있고 한 게시물도 여러 사용자에게 저장될 수 있습니다. 중간 테이블을 명시적인 `Bookmark` 엔티티로 만들고 저장 시각을 함께 보관했습니다.

```java
@Entity
@Table(
    name = "bookmarks",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_bookmarks_user_post",
        columnNames = {"user_id", "post_id"}
    )
)
public class Bookmark {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long bookmarkId;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private User user;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Post post;

    private LocalDateTime createdAt;
}
```

DB에도 `(user_id, post_id)` 유니크 제약을 두었습니다. 애플리케이션의 사전 조회만으로는 동시에 들어온 두 요청을 완전히 막을 수 없으므로 데이터베이스가 마지막 불변식을 지키게 했습니다.

```sql
CREATE TABLE bookmarks (
    bookmark_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    created_at TIMESTAMP(6) NOT NULL,
    CONSTRAINT uk_bookmarks_user_post UNIQUE (user_id, post_id),
    CONSTRAINT fk_bookmarks_user FOREIGN KEY (user_id) REFERENCES users(user_id),
    CONSTRAINT fk_bookmarks_post FOREIGN KEY (post_id) REFERENCES posts(post_id)
);

CREATE INDEX idx_bookmarks_user_created_at
    ON bookmarks (user_id, created_at DESC, bookmark_id DESC);
```

인덱스는 사용자별 북마크를 저장 최신순으로 읽는 조회 패턴에 맞췄습니다.

## 저장과 삭제는 멱등하게 만들었습니다

사용자가 네트워크 지연 중 버튼을 다시 누르거나 클라이언트가 재시도해도 결과가 흔들리지 않도록 서비스 메서드가 이미 저장된 상태와 이미 삭제된 상태를 정상 처리합니다.

```java
@Transactional
public boolean addBookmark(Long userId, Long postId) {
    User user = getActiveUser(userId);
    Post post = getActivePost(postId);

    if (bookmarkRepository.existsByUserAndPost(user, post)) {
        return false;
    }

    bookmarkRepository.save(new Bookmark(user, post));
    return true;
}

@Transactional
public boolean deleteBookmark(Long userId, Long postId) {
    Optional<Bookmark> bookmark = bookmarkRepository.findByUserAndPost(
        getActiveUser(userId),
        getActivePost(postId)
    );

    bookmark.ifPresent(bookmarkRepository::delete);
    return bookmark.isPresent();
}
```

최초 저장은 `BOOKMARK_CREATED`, 이미 저장된 대상의 재요청은 `BOOKMARK_ALREADY_SAVED`로 구분하되 두 응답 모두 최종 상태 `bookmarked: true`를 전달합니다.

```json
{
  "code": "BOOKMARK_CREATED",
  "data": { "postId": 31, "bookmarked": true }
}
```

## 목록 응답에는 현재 사용자의 상태를 배치로 합성했습니다

피드 카드마다 북마크 존재 여부를 개별 조회하면 게시물 수만큼 쿼리가 늘어납니다. 현재 Slice의 게시물 ID를 모아 한 번의 `IN` 쿼리로 저장된 ID 집합을 얻었습니다.

```java
@Query("""
    select bookmark.post.postId
    from Bookmark bookmark
    where bookmark.user.userId = :userId
      and bookmark.post.postId in :postIds
      and bookmark.post.postDeleted = false
    """)
List<Long> findBookmarkedPostIds(Long userId, Collection<Long> postIds);
```

```java
Set<Long> bookmarkedPostIds =
    bookmarkService.findBookmarkedPostIds(userId, postIds);

posts.map(post -> new PostResponse(
    post,
    postService.getPostImageUrl(post),
    bookmarkedPostIds.contains(post.getPostId()),
    likedPostIds.contains(post.getPostId())
));
```

상세 조회는 단건 존재 여부를, 피드 조회는 배치 ID 조회를 사용해 각 요청 형태에 맞는 비용을 선택했습니다.

## 프론트엔드는 즉시 반응하고 실패하면 되돌렸습니다

사용자가 저장 버튼을 누르면 API 응답을 기다리지 않고 아이콘부터 바꿉니다. 요청 중에는 같은 게시물의 버튼을 잠그고, 성공하면 서버 응답으로 확정하며, 실패하면 `before` 상태로 롤백합니다.

```jsx
async function bookmark(postId) {
  const before = posts.find((post) => post.postId === postId);
  if (!before || bookmarking.has(postId)) return;

  setBookmarking((current) => new Set(current).add(postId));
  setPosts((all) => all.map((post) =>
    post.postId === postId
      ? { ...post, bookmarked: !post.bookmarked }
      : post
  ));

  try {
    const result = before.bookmarked
      ? await postApi.deleteBookmark(postId)
      : await postApi.addBookmark(postId);

    const bookmarked = before.bookmarked
      ? false
      : (result?.bookmarked ?? true);

    setPosts((all) => all.map((post) =>
      post.postId === postId ? { ...post, bookmarked } : post
    ));
  } catch (cause) {
    setPosts((all) => all.map((post) =>
      post.postId === postId ? before : post
    ));
  } finally {
    setBookmarking((current) => {
      const next = new Set(current);
      next.delete(postId);
      return next;
    });
  }
}
```

`PostCard`는 `bookmarked`에 따라 stroke/fill SVG와 `aria-pressed`를 동시에 바꿉니다. 시각 상태와 접근성 상태가 같은 데이터에서 파생되므로 서로 어긋나지 않습니다.

## 북마크 전용 화면과 화면 간 동기화

`GET /api/posts/bookmarks?page=0&size=10`은 사용자가 최근 저장한 순서로 Slice를 반환합니다.

```java
Slice<Bookmark>
findAllByUserAndPost_PostDeletedFalseOrderByCreatedAtDescBookmarkIdDesc(
    User user,
    Pageable pageable
);
```

피드나 상세에서 북마크가 바뀌면 상위 `App`의 `bookmarkRefreshKey`를 증가시켰습니다. 북마크 화면이 다시 열릴 때 이 키를 의존성으로 사용해 목록을 새로 조회합니다. 전역 상태 라이브러리를 추가하지 않고도 현재 애플리케이션 규모에 맞는 단순한 동기화 경로를 만들었습니다.

북마크 화면에서도 공용 `PostCard`를 사용하고 좋아요를 연결했습니다. 따라서 저장한 게시물 목록에서도 하트 아이콘과 숫자를 변경할 수 있으며, 백엔드가 내려 준 사용자별 `liked` 상태가 그대로 유지됩니다.

## 검증

백엔드에서는 다음을 통합 테스트로 고정했습니다.

- 동일 북마크 저장과 삭제의 멱등성
- 사용자별 북마크 상태 격리
- 삭제된 게시물 북마크 거부
- 10개 단위 Slice, `hasNext`, 페이지 간 중복 없음
- 최초 저장과 재요청 성공 코드 구분

프론트에서는 저장·새로고침·삭제·실패 롤백·재시도와 SVG 전환을 하나의 사용자 흐름으로 확인했습니다.

## 회고

북마크의 핵심은 boolean이 아니라 “누가 어떤 게시물을 저장했는가”라는 관계였습니다. 관계의 유일성을 DB가 보장하고, 서비스는 멱등성을 제공하며, 응답은 사용자별 상태를 배치로 합성하고, UI는 낙관적 갱신과 롤백을 담당했습니다. 작은 아이콘 하나도 각 계층의 책임을 분명히 나눌 때 새로고침과 화면 이동 뒤까지 일관된 기능이 되었습니다.
